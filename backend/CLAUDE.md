# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project overview

A backend service that scans a single shared Outlook mailbox, extracts tasks from incoming emails, and stores them in a database. Project managers (PMs) log in to view and self-assign tasks.

**Core email handling rules:**
1. New email, task pre-assigned to a PM (email specifies the PM) → create task with `status: assigned`.
2. New email, no PM specified → create task with `status: unassigned`; any PM can self-claim it.
3. Email referencing an existing task → **fully overwrite** the existing record (not a merge). The field(s) that uniquely identify a record are **not finalized yet** — check with the team before relying on any specific field as a dedupe key.
4. Each email body contains a **table** with potentially **multiple task rows** — one email can produce several tasks. Table format (HTML vs. plain text) is not yet confirmed; the parser must be written to tolerate this.

There is no in-process scheduler. Syncing is triggered externally (e.g. a scheduled job hitting the API) by calling `POST /sync/emails`. This keeps the app stateless and friendly to scale-to-zero hosting (e.g. Cloud Run).

## Tech stack

- **Backend framework:** FastAPI (Python)
- **Database:** Supabase (Postgres) — not Firebase/Firestore
- **Email source:** Microsoft Outlook, via Microsoft Graph API (app-only auth against a single shared mailbox)
- **Auth:** Supabase Auth (JWT). PM accounts are provisioned by the dev team (seed script), not self-signup.

## Architecture

Layered, one-directional dependency flow. **A layer may only call the layer directly below it — never sideways, never up.**

```
routers/  →  services/  →  repositories/  →  Supabase (Postgres)
                ↓
            clients/  →  Microsoft Graph API
```

- **`api/v1/routers/`** — HTTP only. Parse request → call one service function → return response. No business logic, no direct DB/Graph calls.
- **`services/`** — business rules and orchestration. Decides *what* should happen (create vs. overwrite, assign vs. unassigned, the self-assign guard). Calls repositories and clients; never talks to Supabase or Graph directly itself.
- **`repositories/`** — the *only* layer allowed to write SQL / call the Supabase client. Pure data access — no business decisions.
- **`clients/`** — wrappers around external APIs we don't own (Microsoft Graph). Knows nothing about "tasks" — just returns raw data.
- **`models/`** — Pydantic schemas, used for both request/response validation and as the data shape contract across layers.
- **`core/`** — cross-cutting concerns: config (env vars) and security (JWT verification).

## Conventions

- Never put a Supabase/SQL call outside `repositories/`.
- Never put a Microsoft Graph call outside `clients/`.
- Business logic (assign/overwrite/validation rules) belongs in `services/`, not `routers/` or `repositories/`.
- `services/parser.py` should stay a pure function where possible (text in, structured data out) — no I/O — to keep it easy to unit test against sample email bodies without a live mailbox or database.
- The self-assign race condition (two PMs claiming the same task) must be handled with an **atomic conditional update** at the database level (`UPDATE ... WHERE status = 'unassigned'`), not with application-level locking.
- `email_service.sync_new_emails()` maps one email → **multiple** parsed task rows, not one-to-one.

## Open decisions (do not assume — confirm with the team before implementing)

- What field(s) uniquely identify a task record for overwrite matching.
- Exact table format inside email bodies (HTML table vs. plain text) — parser should be built defensively until sample emails are available.
- Whether `/sync/emails` is admin-only or callable by any authenticated PM.
